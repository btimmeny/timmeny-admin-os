# 80 — Monday.com Architecture

## Purpose

This document captures the implementation design for Monday.com within Timmeny Admin OS. Monday structure is downstream of the canonical domain model and is optimized for executable work rather than complete operational context.

## Responsibility Boundary

Monday.com owns:

- executable tasks
- task status
- owners
- due dates
- completion and closure

Timmeny Admin OS owns:

- operational-object identity
- evidence classification
- cross-system mappings
- workflow state
- synchronization and verification
- richer context, decisions, dependencies, and audit

PostgreSQL persists the canonical operational state owned by Admin OS. Monday.com remains authoritative for the native execution fields above.

## Current Prototype

The existing Monday workspace remains in use. User-provided screenshots are current evidence until a working connector is available to the operational chat. Selected records may be reconstructed under `operating/` to learn the correct model; this is deliberate curation rather than synchronization.

## Integration Principles

1. Do not import existing Monday data blindly.
2. Clean and normalize tasks, contacts, relationships, and identifiers before migration.
3. Preserve one authoritative owner for each field.
4. Use stable Timmeny IDs and external Monday item IDs; never use titles as identity.
5. Keep rich evidence and relationship history outside Monday unless visibility is operationally necessary.
6. Treat recurring obligations separately from generated Action instances.
7. Make all connector writes idempotent and auditable.
8. Do not create a task until evidence has been classified against an operational object.
9. Synchronize completion before executing dependent dispositions such as archiving an email.

## First Vertical Slice Requirements

The Monday connector must support:

- create a task from an approved workflow
- update a mapped task without duplication
- read current task status and completion
- store or retrieve a stable Timmeny mapping identifier
- link the task to the originating operational object and evidence through Admin OS
- verify the resulting Monday state after each write

The first slice does not require a comprehensive redesign of all boards.

## Design Questions

- What minimum columns are needed for task execution and stable mapping?
- Should personal and career actions share a board, use separate boards, or use views over a common model?
- Which Objective or Program reference must be visible in Monday?
- Which evidence reference should be visible versus retained only in Admin OS?
- How should existing duplicate and stale items be cleaned before synchronization?
- Which recurrence capabilities should remain native to Monday and which should be generated by Admin OS?

## Design Backlog

- Inventory existing boards, groups, columns, automations, and naming conventions.
- Select the board and minimum columns for the first Gmail-to-task slice.
- Define stable mapping and idempotency fields.
- Define task creation, update, completion, and verification contracts.
- Define cleanup and migration rules for existing items.
- Defer broader Objectives, Entities, Opportunities, Properties, Accounts, and Obligations board decisions until real workflow evidence requires them.

## Promotion Rule

A proposed Monday structure is implemented only when required by a validated operational workflow. The first priority is reliable task execution, not representing the entire domain model inside Monday.
