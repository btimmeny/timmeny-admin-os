# Devin Implementation Brief — Review Scope Control and Gmail Undo

Implement strict end-to-end scope control for Admin OS review actions so the exact item set explicitly selected by Brian is preserved through decision, preparation, confirmation, execution, verification, and audit. When a user selects specific displayed rows, ranges, exclusions, or named subsets, persist the resolved ordered `item_ids` as the latest explicit scope for that action intent and require `prepareReviewActions` to receive those exact `item_ids`; capability-wide preparation must be rejected whenever the latest explicit scope is narrower than the capability. The preparation response must return one prepared action per selected item with `action_id`, `item_id`, canonical action, capability key, preparation state, and a server-issued immutable scope identifier or revision; preparation must fail atomically if it adds unselected items, omits selected items, changes an action, includes an ineligible item, or cannot establish a one-to-one mapping. Add a server-side execution guard that requires the exact prepared `action_ids` plus the matching scope identifier or revision, compares them with the user’s latest explicit scope, and rejects execution if the action set is broader, narrower, stale, superseded, duplicated, or otherwise mismatched; executing by capability key alone must be prohibited for narrower selections. Confirmation summaries must be generated from the server-returned prepared actions, not inferred from prior decisions, and the API must expose enough data to state exactly which items are included and excluded. Preserve idempotency and item-level audit history for bulk decisions and actions. Add a canonical reversible Gmail action such as `restore_gmail_thread_from_trash` that removes `TRASH` and restores the thread to the appropriate non-Trash state, verifies the resulting Gmail labels, records the original Trash action relationship, and follows the same decision → prepare → explicit confirmation → execute → verify lifecycle; expose restore only when the thread is currently in Trash and restoration is permitted. Add regression coverage for the reported incident: given 22 approved Admin items, selecting rows 1–3 and 5–20 must resolve exactly 19 item IDs, prepare exactly 19 actions, return exactly 19 action IDs, require execution with those 19 IDs, execute exactly those 19 Gmail Trash changes, and leave rows 4, 21, and 22 untouched; tests must also prove that capability-wide preparation or execution is rejected, stale or expanded scopes are rejected, confirmation data matches the prepared set, and every Trash action can be restored through the new undo path.
